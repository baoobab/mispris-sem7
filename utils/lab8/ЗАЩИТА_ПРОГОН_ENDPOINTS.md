# Задание №8: прогон эндпоинтов для защиты

Сценарий: пицца с выбираемым диаметром. Система подбирает норму сыра, включает добавку по условию, раскрывает состав соуса и суммирует томаты из двух ветвей.

## 1. Запуск

PowerShell, из корня проекта:

```powershell
Set-Location 'C:\Users\user\Desktop\6mispris-sem7'
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn src.main:app --host 127.0.0.1 --port 8000
```

Если сервер уже работает, использовать его; после обновления кода перезапустить. Адрес БД берётся из настроек проекта. Команды выше не пересоздают БД и не загружают сидер.

Открыть [общий Swagger](http://localhost:8000/docs). Если сервер запущен на другом порту, заменить `8000` в адресе. Для задания №8 нужен раздел **«Спецификации с вариантами (№8)»**. Подготовка справочников и создание варианта используют также разделы предыдущих заданий.

**Не открывать `/docs/lab7` для этого показа:** там отображаются только маршруты задания №7.

## 2. Подготовка данных перед защитой

Этот раздел выполнить заранее один раз. Во время защиты начинать с раздела 3. Все запросы выполняются через `Try it out` → `Execute` в Swagger.

Идентификаторы из ответов записывать в таблицу ниже. Это обозначения для подстановки, а не фиксированные ID. В шаблонах JSON заменить слова `CLASS`, `PIZZA` и т. п. настоящими числами **без кавычек**; до подстановки такие шаблоны не являются готовым JSON.

| Обозначение | Что записать |
| --- | --- |
| `TYPE_NUMBER` | ID значения числового типа параметра |
| `TYPE_ASSEMBLY` / `TYPE_DETAIL` / `TYPE_MATERIAL` | ID типов изделия `assembly` / `detail` / `material` |
| `UNIT_PIECE` / `UNIT_KG` / `UNIT_G` | ID единиц «шт» / «кг» / «г» из `unit_simple` |
| `CLASS` | ID нового класса пицц |
| `DIAMETER` | ID нового параметра `lab8_diameter` |
| `PIZZA` / `SAUCE` / `TOMATO` / `CHEESE` / `HERB` | ID пяти созданных изделий |
| `CHEESE_GRAMS` | ID единицы количества сыра «г» из `unit_quantity` |
| `F_SMALL` / `F_LARGE` / `F_HERB` | ID трёх функций включения |
| `ROW_SMALL` | ID строки BOM с нормой сыра 100 г |
| `VARIANT` | ID созданного варианта пиццы |

### 2.1. Найти существующие типы и единицы

1. `GET /api/enums/types?limit=1000` — найти типы перечислений с `code = param_type` и `code = item_type`.
2. Для каждого выполнить `GET /api/enums/values/by-type/{enum_type_id}`.
3. В `param_type` выбрать числовой тип с `code = number`, `real`, `int` или `integer` → `TYPE_NUMBER`. Для диаметров 25, 30, 36 подойдёт любой из этих типов.
4. В `item_type` найти `assembly`, `detail`, `material` и записать их ID.
5. `GET /api/units/?limit=1000` — найти «шт», «кг», «г» и записать ID.

Если `param_type` отсутствует, создать его через `POST /api/enums/types`:

```json
{"code":"param_type","name":"Тип параметра"}
```

Затем `POST /api/enums/values`, подставив полученный ID типа вместо `PARAM_TYPE`:

```json
{"enum_type_id":PARAM_TYPE,"order_number":1,"code":"number","name":"Число"}
```

Если `param_type` существует, но числового значения нет, добавить значение в него со свободным `order_number`. Не создавать второй тип перечисления с тем же кодом.

Если единицы отсутствуют, создать недостающие через `POST /api/units/`:

```json
{"code":"796","name":"Штука","cond_symbol_1":"шт"}
```

```json
{"code":"166","name":"Килограмм","cond_symbol_1":"кг"}
```

```json
{"code":"163","name":"Грамм","cond_symbol_1":"г"}
```

Перед созданием проверить, что коды свободны. Для расчёта в этом сценарии коэффициент граммов к килограммам задаётся отдельно в `unit_quantity` сыра.

### 2.2. Создать класс и параметр

`POST /api/classifiers/items` → **201**, сохранить `id` как `CLASS`:

```json
{"name":"Пиццы для защиты №8","parent_id":null}
```

`POST /api/parameters/` → **201**, сохранить `id` как `DIAMETER`:

```json
{"code":"lab8_diameter","name":"Диаметр пиццы","param_type_id":TYPE_NUMBER}
```

`POST /api/configuration/classes/{CLASS}/parameters` → **201**:

```json
{"parameter_id":DIAMETER,"required":true,"flag_conf":true,"min_value":20,"max_value":40}
```

### 2.3. Создать изделия

Пять раз выполнить `POST /api/items/`, каждый раз сохранить возвращённый `id`:

```json
{"number":"LAB8-PIZZA","name":"Пицца для защиты №8","item_class_id":CLASS,"item_type_id":TYPE_ASSEMBLY}
```

```json
{"number":"LAB8-SAUCE","name":"Соус для защиты №8","item_type_id":TYPE_DETAIL}
```

```json
{"number":"LAB8-TOMATO","name":"Томаты для защиты №8","item_type_id":TYPE_MATERIAL}
```

```json
{"number":"LAB8-CHEESE","name":"Моцарелла для защиты №8","item_type_id":TYPE_MATERIAL}
```

```json
{"number":"LAB8-HERB","name":"Базилик для защиты №8","item_type_id":TYPE_MATERIAL}
```

Ожидается **201** для каждого изделия. `PIZZA` — ID первого, остальные обозначения соответствуют именам.

### 2.4. Назначить единицы количества

`POST /api/items/units` выполнить для каждой строки таблицы, используя такой шаблон:

```json
{"item_id":PIZZA,"unit_simple_id":UNIT_PIECE,"coefficient":1,"is_base":true}
```

| item_id | unit_simple_id | coefficient | is_base |
| --- | --- | --- | --- |
| `PIZZA` | `UNIT_PIECE` | 1 | true |
| `SAUCE` | `UNIT_KG` | 1 | true |
| `TOMATO` | `UNIT_KG` | 1 | true |
| `CHEESE` | `UNIT_KG` | 1 | true |
| `HERB` | `UNIT_KG` | 1 | true |
| `CHEESE` | `UNIT_G` | 0.001 | false |

Ожидается **201**. У последней строки сохранить её `id` как `CHEESE_GRAMS`. Это ID единицы **количества конкретного изделия**, а не `UNIT_G` из справочника общих единиц.

`PUT /api/configuration/items/{PIZZA}/configurator` → **200**, `kind = template`.

### 2.5. Создать функции включения

Каждый запрос — `POST /api/configured-bom/functions`, ожидается **201**.

Маленькая пицца: диаметр < 35 → сохранить `id` как `F_SMALL`:

```json
{
  "code":"Lab8Small",
  "name":"Диаметр меньше 35",
  "conjunctions":[
    [{"parameter_id":DIAMETER,"operator":"lt","value_number":35}]
  ]
}
```

Большая пицца: диаметр ≥ 35 → `F_LARGE`:

```json
{
  "code":"Lab8Large",
  "name":"Диаметр от 35",
  "conjunctions":[
    [{"parameter_id":DIAMETER,"operator":"ge","value_number":35}]
  ]
}
```

Добавка: (диаметр ≥ 35 И диаметр ≤ 40) ИЛИ диаметр = 30 → `F_HERB`:

```json
{
  "code":"Lab8Herb",
  "name":"Базилик для большой пиццы или диаметра 30",
  "conjunctions":[
    [
      {"parameter_id":DIAMETER,"operator":"ge","value_number":35},
      {"parameter_id":DIAMETER,"operator":"le","value_number":40}
    ],
    [{"parameter_id":DIAMETER,"operator":"eq","value_number":30}]
  ]
}
```

Внешний массив объединяет группы через **ИЛИ**; предикаты внутри одной группы объединяются через **И**. Это хранится в реляционных таблицах, JSON используется для передачи запроса.

### 2.6. Добавить позиции BOM

Для первых пяти строк таблицы выполнить `POST /api/configured-bom/items/{PIZZA}/positions`. Для последней — тот же маршрут с `{SAUCE}`.

Шаблон запроса для позиции без условия:

```json
{"component_item_id":SAUCE,"quantity":0.2,"for_quantity":1,"function_id":null,"order_number":1}
```

| Родитель | component_item_id | quantity | for_quantity | function_id | unit_quantity_id | order_number |
| --- | --- | --- | --- | --- | --- | --- |
| `PIZZA` | `SAUCE` | 0.2 | 1 | null | не передавать | 1 |
| `PIZZA` | `TOMATO` | 0.03 | 1 | null | не передавать | 2 |
| `PIZZA` | `CHEESE` | 100 | 1 | `F_SMALL` | `CHEESE_GRAMS` | 3 |
| `PIZZA` | `CHEESE` | 200 | 1 | `F_LARGE` | `CHEESE_GRAMS` | 4 |
| `PIZZA` | `HERB` | 0.005 | 1 | `F_HERB` | не передавать | 5 |
| `SAUCE` | `TOMATO` | 2 | 4 | null | не передавать | 1 |

Конкретный шаблон для маленькой нормы сыра:

```json
{
  "component_item_id":CHEESE,
  "quantity":100,
  "for_quantity":1,
  "unit_quantity_id":CHEESE_GRAMS,
  "function_id":F_SMALL,
  "order_number":3
}
```

Ожидается **201** для каждой строки. У маленькой нормы сыра сохранить возвращённый `id` как `ROW_SMALL`.

Позиция соуса означает: на 4 кг соуса нужно 2 кг томатов. На 1 кг соуса — 0.5 кг томатов. На одну пиццу нужно 0.2 кг соуса, значит через соус расходуется 0.1 кг томатов. Ещё 0.03 кг томатов входят в пиццу напрямую.

## 3. Основной показ за 5–7 минут

Перед началом подставить свои ID в маршруты и тела запросов. В Swagger числа вводятся в отдельные поля `item_id`, `function_id` и т. п.

| Шаг | Запрос | Что показать |
| --- | --- | --- |
| 1 | `GET /api/configuration/items/{PIZZA}/parameters` | Параметр `lab8_diameter`, диапазон 20–40, обязательность |
| 2 | `GET /api/configured-bom/functions/{F_HERB}` | Две группы ИЛИ, внутри первой два предиката И; ссылки на параметр |
| 3 | `GET /api/items/{PIZZA}/bom` | Исходный состав: обе альтернативные нормы сыра и ссылки `configuration_function_id` |
| 4 | `POST /api/configured-bom/items/{PIZZA}/preview` с диаметром 25 | Выбраны 100 г сыра; базилик и строка 200 г отсутствуют |
| 5 | Тот же запрос с диаметром 30 | Сыр 100 г; базилик появился по второй группе ИЛИ |
| 6 | Тот же запрос с диаметром 36 и количеством 2 | Сыр 200 г на пиццу; раскрыт соус; посчитаны сводные нормы на две пиццы |
| 7 | `POST /api/configuration/items/{PIZZA}/variants` | Вариант сохраняется как изделие с выбранными параметрами |
| 8 | `GET /api/configured-bom/items/{VARIANT}/specification?quantity=2` | Те же нормы уже из сохранённых значений варианта |
| 9 | Неверный диаметр 50 через `preview` | **400**, значение вне диапазона |

### Шаг 4. Диаметр 25, одна пицца

`POST /api/configured-bom/items/{PIZZA}/preview`:

```json
{"values":{"lab8_diameter":25},"quantity":1}
```

Ожидается **200**. В `nodes` находятся соус, томаты внутри соуса, прямые томаты и строка сыра 100 г. Базилик отсутствует. Сыр 200 г отсутствует.

В `norms` только конечные материалы:

| Материал | total_quantity | Базовая ЕИ |
| --- | --- | --- |
| Томаты | 0.13 | кг |
| Моцарелла | 0.1 | кг |

Соус есть в дереве `nodes`, но отсутствует в сводных нормах `norms`: он раскрывается до томатов.

### Шаг 5. Диаметр 30, одна пицца

```json
{"values":{"lab8_diameter":30},"quantity":1}
```

Ожидается **200**. Томаты — 0.13 кг, сыр — 0.1 кг, базилик — 0.005 кг. Добавка прошла вторую группу функции: `диаметр = 30`.

### Шаг 6. Диаметр 36, две пиццы

```json
{"values":{"lab8_diameter":36},"quantity":2}
```

Ожидается **200**:

| Материал | total_quantity | Расчёт |
| --- | --- | --- |
| Томаты | 0.26 кг | `(0.2 × 2 / 4 + 0.03) × 2` |
| Моцарелла | 0.4 кг | `200 × 0.001 × 2` |
| Базилик | 0.01 кг | `0.005 × 2` |

В `nodes` у томатов через соус путь длиннее, чем у прямых томатов. Поле `norm` — расход на **одну** пиццу; `total_quantity` — расход на запрошенное количество. Порядок строк не является критерием проверки: сравнивать по `component_item_id` и названию.

В ответах Decimal может отображаться строкой, например `"0.260000000000"`; проверять числовое значение.

Фраза для преподавателя: «Правило вычисляется на каждой позиции при обходе. Строки без функции включаются всегда. Для вложенных материалов перемножаются нормы по пути, одинаковые материалы из разных ветвей суммируются».

### Шаг 7. Сохранить вариант

`POST /api/configuration/items/{PIZZA}/variants`:

```json
{
  "number":"LAB8-PIZZA-36-DEF1",
  "name":"Пицца 36 см для защиты №8",
  "values":{"lab8_diameter":36}
}
```

Ожидается **201**. Сохранить **`item.id`** как `VARIANT`. В ответе `configuration.kind = variant`, `configuration.template_id = PIZZA`.

### Шаг 8. Рассчитать сохранённый вариант

`GET /api/configured-bom/items/{VARIANT}/specification`, поле `quantity = 2`, поле `at` оставить пустым.

Ожидается **200**. `item_id = VARIANT`, `source_item_id = PIZZA`; нормы совпадают с шагом 6. Значения параметров повторно передавать не нужно.

### Шаг 9. Показать валидацию

`POST /api/configured-bom/items/{PIZZA}/preview`:

```json
{"values":{"lab8_diameter":50},"quantity":1}
```

Ожидается **400**, сообщение о выходе параметра за диапазон. Ошибочный расчёт не создаёт вариант и не изменяет BOM.

## 4. Дополнительные проверки, если преподаватель попросит

### Смена условия существующей позиции

Выполнять после основного показа. Для базилика:

`PUT /api/configured-bom/items/{PIZZA}/components/{HERB}/condition`:

```json
{"function_id":null,"reason":"Защита: сделать добавку безусловной"}
```

Ожидается **200**, возвращается новый `bom_id`. Повторить `preview` с диаметром 25: базилик появился, 0.005 кг на пиццу.

`GET /api/items/{PIZZA}/bom/changes` — показать историю; у новой версии `configuration_function_id = null`, у предыдущей сохранена ссылка на `F_HERB`.

Вернуть исходное поведение тем же PUT:

```json
{"function_id":F_HERB,"reason":"Защита: вернуть исходное условие"}
```

Для сыра с несколькими альтернативными строками использовать изменение **по bom_id**, а не по ID компонента:

`PUT /api/configured-bom/items/{PIZZA}/positions/{ROW_SMALL}`:

```json
{
  "component_item_id":CHEESE,
  "quantity":120,
  "for_quantity":1,
  "unit_quantity_id":CHEESE_GRAMS,
  "function_id":F_SMALL,
  "order_number":3,
  "reason":"Защита: изменить норму маленькой пиццы"
}
```

Ожидается **200** и новая версия строки с новым `id`. Сохранить его вместо `ROW_SMALL`. При диаметре 25 сыр теперь 0.12 кг. Для восстановления повторить PUT с **новым** ID строки и `quantity = 100`.

### Запрет удаления используемой функции

`DELETE /api/configured-bom/functions/{F_LARGE}` → **409**: функция используется в спецификации или её истории. Данные сохраняются.

### Условие на вложенном уровне

`PUT /api/configured-bom/items/{SAUCE}/components/{TOMATO}/condition`:

```json
{"function_id":F_HERB,"reason":"Защита: условие на вложенном компоненте"}
```

Повторить расчёт пиццы диаметром 25 на одну штуку: в `nodes` остаётся соус, но его строка томатов исключена. В `norms` томатов **0.03 кг**, только из прямой ветви. Сам соус не превращается в конечный материал, поскольку у него есть исходная спецификация.

При диаметре 36 условие истинно, поэтому томатов снова **0.13 кг на одну пиццу**. Это показывает вычисление условия на вложенном уровне с параметрами корневого варианта.

Восстановить исходное состояние тем же PUT с телом:

```json
{"function_id":null,"reason":"Защита: восстановить безусловный состав соуса"}
```

### Отсутствие обязательного параметра

`POST /api/configured-bom/items/{PIZZA}/preview` с телом:

```json
{"values":{},"quantity":1}
```

Ожидается **400**: обязателен `lab8_diameter`.

### Отрицательное количество

```json
{"values":{"lab8_diameter":30},"quantity":-1}
```

Ожидается **422**: количество должно быть больше нуля.

## 5. Соответствие последним двум страницам ТЗ

| Требование | Где реализовано | Что показать |
| --- | --- | --- |
| Позиция спецификации ссылается на функцию | `item_bom.configuration_function_id` | GET исходного BOM |
| Функция, группы ИЛИ, предикаты внутри И | `configuration_function` + `bom_function`, `bom_conjunction`, `bom_predicate` | GET функции `F_HERB` |
| Предикат: параметр + оператор + значение | FK на `parameter`, `rule_operator`; типизированное значение, для перечисления FK на `enum_value` | Тело функции в Swagger |
| Вычислить условие позиции | Хранимая функция PostgreSQL `lab8_eval` | Различия диаметров 25, 30, 36 |
| Рекурсивно раскрыть спецификацию | `lab8_tree`, с учётом действующих версий через `lab8_effective` | Путь пицца → соус → томаты в `nodes` |
| Перемножить нормы и сложить расход по ветвям | `lab8_norms` | Томаты 0.26 кг на две пиццы |

Хранимые функции вызываются через API расчёта. В Swagger отдельного маршрута с именем `lab8_eval` нет: результат вычисления виден по включённым позициям. `preview` и `specification` возвращают и дерево, и сводные нормы.

## 6. Короткие ответы на вопросы

- **Чем №8 отличается от №7?** №7 проверяет допустимость сочетания параметров и сохраняет вариант. №8 определяет состав этого варианта и требуемое количество материалов.
- **Зачем две строки сыра?** Один компонент имеет разные нормы при разных условиях. Правила `< 35` и `≥ 35` взаимно исключаются, поэтому в результат попадает одна строка. Если два условия одновременно истинны, включаются обе строки и их расход суммируется: система не выбирает победителя по приоритету.
- **Что происходит с дочерними строками исключённой сборки?** Обход этой ветви не выполняется, её материалы не попадают в расчёт.
- **Как задать замену материала?** Добавить строки разных материалов и назначить им взаимоисключающие функции. При расчёте включится материал, условие которого истинно; отдельной строковой колонки с именем заменяемого материала не требуется.
- **Что значит отсутствие функции?** Позиция включается всегда. Пустой список групп функции — FALSE; пустая группа И — TRUE.
- **Сколько добавлено таблиц?** Три: маркер функции с телом ДНФ, конъюнкции и предикаты. Заголовок функции, параметры, операторы, значения перечислений, изделия, единицы и BOM переиспользованы.
- **Откуда берутся значения сохранённого варианта?** Из `variant_parameter_value`; ссылка на шаблон берётся из `item_configuration`.
- **Где считать именно конфигурируемый состав?** Через `/api/configured-bom/.../preview` или `/specification`. Обычный `/api/items/{id}/bom` показывает исходные позиции, включая альтернативы.
- **Создание варианта копирует весь рассчитанный BOM?** Нет. Вариант хранит параметры и ссылку на шаблон; состав рассчитывается по действующим строкам и правилам при запросе.
- **Исторический запрос фиксирует прежние тела правил?** Нет. `at` выбирает версии строк BOM; тело редактируемой функции не версионируется. Для показа истории используются смена ссылки/нормы строки и `bom/changes`, а не обещание полного снимка прежних правил.

## 7. Повторный показ

Подготовку раздела 2 повторно не выполнять: обозначения изделий и коды функций уникальны. Найти созданные изделия можно через `GET /api/items/?name=для%20защиты%20№8`, функции — через `GET /api/configured-bom/functions`, параметры — через `GET /api/parameters/?limit=1000`.

Перед повторным показом проверить исходные нормы 100/200 г, вернуть условие базилика `F_HERB` и снять условие вложенной строки томатов, если выполнялись дополнительные изменения. Основной показ не меняет эти настройки. Для нового варианта заменить обозначение `LAB8-PIZZA-36-DEF1` на свободное, например `LAB8-PIZZA-36-DEF2`, либо использовать уже сохранённый `VARIANT`.

Не запускать сидеры для восстановления этого сценария: они для него не нужны. Не использовать числовые ID стенда №7 — здесь все ID берутся из ответов текущей БД.
